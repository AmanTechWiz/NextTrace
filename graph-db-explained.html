Graph databases, explained with our own project

Enough to understand the architecture and explain it to judges. All the examples use NextTrace: a small online shop made of services that call each other.

1 · The one idea: rows vs. dots and arrows

A relational database (Oracle, Postgres) stores everything as rows in tables. Connections are just matching values: a row in calls says "frontend calls checkout". To follow a connection, the database has to look it up (a JOIN) every time.

A graph database stores things (nodes, the dots) and connections (relationships, the arrows) as first-class data. Following a connection doesn't need a lookup: the arrow is already stored with the thing.

Oracle: a table of connections

You see rows. The shape (who depends on whom, how deep) is hidden until you query for it.

FalkorDB: the same data as a graph

You see the shape. Payment is failing, and the amber path shows how the failure reaches users.

The vocabulary: node = a thing (a Service). label = its type (:Service). relationship = a typed arrow (:CALLS). properties = key–value data on either ({name:'payment'}). That's the entire data model, called a property graph.

2 · Same question, two languages

Question: "Payment is down. Which services break because of it?" Something breaks if it calls payment directly, or calls something that calls payment, and so on. The depth isn't known in advance.

Oracle SQL: recursive query
WITH upstream (name, depth) AS (
  SELECT caller, 1 FROM calls
  WHERE callee = 'payment'
  UNION ALL
  SELECT c.caller, u.depth + 1
  FROM calls c
  JOIN upstream u ON c.callee = u.name
  WHERE u.depth < 6
)
SELECT DISTINCT name FROM upstream;

Works, but you're hand-writing a loop of JOINs. Each level is another lookup.

Cypher: describe the shape
MATCH (up:Service)-[:CALLS*1..6]->(:Service {name:'payment'})
RETURN DISTINCT up.name

You draw the pattern, and *1..6 means "follow 1 to 6 arrows". The database does the walking.

Harder question: "Show me the route from the user's entry point to the failing service." In SQL you'd also have to build the path string and stop at the first (shortest) one: painful. In Cypher:

MATCH (a:Service {name:'frontend'}), (b:Service {name:'payment'})
WITH shortestPath((a)-[:CALLS*]->(b)) AS p
RETURN [n IN nodes(p) | n.name]      // → ['frontend', 'checkout', 'payment']

This is the "show the path behind the answer" that the hackathon asks for, in one query. (FalkorDB rule: both endpoints must be found before calling shortestPath, which is why the MATCH comes first.)

3 · Why graphs are fast at this

Relational: phone book every hop

Each hop = "find all rows where callee = X" in an index. It's like looking up every friend's friend in a phone book. 1 hop is cheap. 5 hops means 5 rounds of lookups, and the work multiplies with fan-out.

Graph: just follow the arrow

Each thing already knows its arrows. A hop is "go to my neighbours", so cost grows with how much of the graph you actually touch, not with how big the whole table is.

FalkorDB's specific trick: the graph is a grid of 1s

FalkorDB stores the arrows as a sparse adjacency matrix: row = from, column = to, a 1 means "there's an arrow". "Sparse" means only the 1s are stored, so it's tiny in memory.

CALLS matrix (from → to)

front11
check11

Why a grid?

One hop = one matrix multiplication. Two hops = multiply twice. FalkorDB's docs give the example "friends of friends = F²".

Matrix maths is something computers are extremely good at. FalkorDB uses GraphBLAS, a standard high-performance library for exactly this. It can also reorder and parallelise the multiplications to keep things fast.

Each relationship type gets its own matrix, and each label gets one too. Adding an edge just flips a cell to 1.

Compared to Oracle: Oracle is a disk-first, general-purpose row store with a huge feature set (transactions across tables, reporting, PL/SQL). FalkorDB is a memory-first, specialised engine: one job, traversing connections fast enough to run on every step of an AI agent.

A quick correction: FalkorDB didn't invent Cypher. Neo4j created it, and it was later opened up as openCypher. FalkorDB implements it and adds its own extras (like the algo.* procedures below). The core idea is ASCII art: () is a node and --> is an arrow, so the query looks like the picture.

Read one of our real queries, line by line

MATCH (i:Incident {id:$id})-[:HAS_SIGNAL]->(:Signal)-[:ON]->(s:Service)   // services with alarms in this incident
WITH collect(DISTINCT s) AS bad                                         // put them in a list called "bad"
UNWIND bad AS s                                                         // look at each one
OPTIONAL MATCH (s)-[:CALLS*1..4]->(d:Service) WHERE d IN bad              // does it depend on another bad one?
RETURN s.name, count(d) AS badDeps ORDER BY badDeps ASC                // 0 bad dependencies = likely the culprit

In plain words: "among the services that are alarming, find the one that isn't just a victim of another alarming service below it." That's root-cause analysis as a graph pattern.

6 · Built-in algorithms (the "power tools")

Queries answer questions you can describe. Algorithms answer questions about the whole shape. FalkorDB ships these in the database; you call them with CALL algo.<name>(…). Check the exact arguments on each algorithm's docs page.

BFS

Spread outward ring by ring from one node.

Ours: blast radius, "everything within 3 hops of payment".

Shortest path

The quickest route between two nodes.

Ours: the explanation path, frontend → … → culprit.

PageRank

"Important" nodes are ones that many important nodes point to (Google's original idea).

Ours: which services are most critical overall.

Betweenness

Which nodes sit on the most routes, like a bridge everyone must cross.

Ours: single points of failure.

WCC

Groups of nodes connected at all, ignoring arrow direction.

Ours: are two alarms even related?

CDLP

Finds clusters or communities by letting labels spread among neighbours.

Ours: optional, grouping services into teams or domains.

Also available: A* (pathfinding with coordinates), harmonic centrality, minimum spanning forest, max flow.

7 · When a graph is the wrong tool

JobBetter fitWhy
Monthly revenue report, big sums over millions of rowsSQL / warehouseNo connections to follow; it's scanning and adding
Simple CRUD app (users, orders)SQLShallow, fixed relationships; mature tooling
"Find text similar to this"Vector searchThat's about meaning, not connections
Unknown-depth chains, paths, "who's connected to whom"GraphThis is exactly what it's built for
This is also the hackathon's removal test: if our app works just as well with a plain table, the graph is "decoration". NextTrace's core questions (culprit, blast radius, path, similar past incidents) are all multi-hop, which is why it passes.

8 · NextTrace's graph, and how to explain it in 30 seconds

(:Service)-[:CALLS]->(:Service)                    // the map of the system
(:Signal)-[:ON]->(:Service)                       // alarms, attached to where they fired
(:Incident)-[:HAS_SIGNAL]->(:Signal)              // which alarms belong to this outage
(:Incident)-[:CAUSED_BY]->(:Service)              // what we concluded (episodic memory)
(:Incident)-[:APPLIED {worked}]->(:Runbook)       // what fixed it (procedural memory)
(:Agent)-[:WROTE]->(:Incident)                    // who said what (provenance, handoffs)
Say this to judges: "The services and how they call each other are a graph. Alarms attach to services. To find the culprit, the agent walks the graph looking for the alarming service that isn't just a victim of another one, and the walk itself is the explanation. Every incident and every fix that worked is saved back into the same graph, so next time the agent recognises the pattern. Each customer gets their own isolated graph, and agents hand work to each other through it. Take the graph away and the agent is just guessing from a list of alarms, and our benchmark measures exactly how much worse it gets."
Sources: FalkorDB internals (sparse matrices, GraphBLAS, traversal = matrix multiplication), Cypher functions (shortestPath rules), algorithms, docs home. Concurrency, from the concurrency page: one write query at a time per graph (queued in order), reads don't block each other, and each write query is all-or-nothing.
